# CybitX CEX 应用宪章

## 核心原则

### I. 安全与合规优先（强制性）

CybitX 是一款中心化交易所（CEX）应用。任何可能影响用户资金、市场公平性
或敏感数据的功能，**必须**在设计、实现与评审阶段，将安全与合规放在首位，
而不是事后补救。

- 所有涉及登录/注册、账号管理、下单、平仓、充提币、杠杆调整、跟单、资产
  展示等功能，**必须**在规格文档中写清安全与合规要求。
- 凭证、密钥、私钥、用户隐私信息（PII）等敏感数据**禁止**写入代码仓库，
  必须使用平台推荐的安全存储方式进行管理。
- 与后端服务的网络通信**必须**使用 TLS，并按后端约定正确校验主机与证书。
- 监管/业务风险控制（如 KYC/AML、地域限制、交易限额、风险提示等），
  **必须**在对应的 UI 流程中清晰呈现。
- 所有安全敏感改动（包括第三方 SDK 升级），**必须**至少由一名工程师进行
  专门的安全影响评审。

理由：CEX 应用直接承载用户资金与交易能力，一次安全或合规事故就可能带来
不可逆的财务与口碑损失。

### II. 交易体验与性能

交易体验需要尽量接近甚至优于主流 CEX（例如币安）的水准，尤其是在价格
发现与下单等高频交互场景。

- 行情、现货、合约、跟单与资产等核心界面，在正常使用场景下，**应**以
  60 fps 为目标进行优化。
- App 首次冷启动，以及切换到各大主 Tab（行情、合约、现货、跟单、资产）
  的首屏加载时间，**必须**在功能规格中给出可度量的目标（例如：参考机型
  上小于 2 秒）。
- 所有页面在进入后、数据加载完成前，**必须**显示占位动画（Skeleton Screen
  或 Shimmer 效果），避免空白页面或突兀的内容闪现，提升用户感知的流畅度。
- 所有列表页面（如行情列表、订单列表、资产列表、交易员列表等），**必须**
  支持下拉刷新功能，让用户可以主动更新数据。
- 实时行情与订单数据更新，**必须**通过合理划分状态与 Riverpod 的精细化
  刷新策略，尽量减少不必要的 Widget 重建。
- 关键操作（如下单、调杠杆、平仓、资产划转、开启/停止跟单）的交互流程
  **必须**简洁、确认步骤清晰，且在业务允许的范围内尽量可回滚。
- 所有高价值交互，**必须**在规格文档中给出可验证的验收标准（例如：从
  行情页下一个市价单最多不超过 N 次点击）。

理由：交易用户会自然地将 CybitX 与头部交易应用进行对比，流畅与可预期的
体验，是建立信任与留存的前提。占位动画和下拉刷新是现代移动应用的标准
交互模式，可以显著提升用户感知的响应速度和控制感。

### III. 行情、合约、现货、跟单、资产的清晰领域边界

应用围绕五大业务域构建：**行情、合约（合约/永续）、现货、跟单、资产**。
每个领域都**必须**有清晰的职责边界与接口，以支持团队独立演进。

- 每个领域的代码**推荐**放在独立的特性模块/包中，例如：
  `lib/features/markets`、`lib/features/futures`、
  `lib/features/spot`、`lib/features/copy_trading`、
  `lib/features/assets`。
- 设计系统、网络、埋点、认证、国际化等通用能力，**必须**放在共享模块中，
  且不得依赖具体业务领域代码。
- 每个功能规格文档，**必须**说明它涉及哪些领域模块，以及依赖哪些共享模块。
- 跨领域流程（例如：从行情跳转到现货下单，从合约盈亏跳转到资产概览），
  **必须**在规格文档中写清边界与责任划分，避免"隐式耦合"。

理由：清晰的领域边界可以降低偶然复杂度，让功能实现更容易推理，也有利于
各大业务线独立演化。

### IV. 可靠性、可观测性与故障响应

移动端必须提供足够的可观测性，以便在生产环境中快速发现、定位并缓解问题，
尤其是与交易和资产相关的关键流程。

- 与后端的每一次网络交互，**必须**记录足够的元数据（请求类型、接口、
  关联 ID、高层状态等），同时兼顾隐私与安全要求。
- 关键失败场景（如下单失败、仓位显示异常、资产余额异常、登录失败等），
  **必须**向用户给出可理解、可行动的错误提示，并向埋点/日志系统输出结构化
  事件。
- 涉及关键交易或资产流程的规格文档，**必须**定义对应的监控/告警预期
  （例如：错误率上限、时延阈值），以便后端与移动端协同验证。
- App **应**尽量支持"安全降级"：局部失败（例如某个 Tab 加载失败），不应
  导致整 App 崩溃，并应为用户提供重试等恢复路径。

理由：在金融场景中，静默失败与缺乏可观测性，往往与直接崩溃一样危险。

### V. 规格驱动与测试优先交付

除极小改动外，任何非 trivial 的需求，**必须**从书面规格与实现计划开始。
规格、计划与任务列表并非形式主义，而是产品与研发之间的契约，也是评审的
主要依据。

- 使用 `/speckit.specify` 编写功能规格文档，明确用户故事、需求与验收标准，
  在大规模实现开始前完成。
- 使用 `/speckit.plan` 推导技术实现方案，包含宪章检查结果、架构决策与对
  工程结构的影响。
- 使用 `/speckit.tasks` 生成按用户故事拆分的可执行任务列表，使每个用户
  故事都可以独立实现与测试。
- 对于高风险流程（安全、下单、充提、杠杆、开启/停止跟单等），**建议**
  在实现前或实现过程中，优先设计对应的单元/组件/集成测试，并保证可以从
  用户故事与需求追溯到具体测试用例。

理由：规格驱动与测试优先可以减少沟通误差，使评审更聚焦，并为复杂交易
行为留下长期可维护的文档与测试资产。

### VI. 国际化与多语言体验

CybitX 面向全球用户，多语言体验是产品价值与合规沟通的重要组成部分。App
**必须**从一开始就将国际化（i18n）与本地化（l10n）视为一等公民能力，而不是
发布后的"加装组件"。

- 当前版本**至少**支持简体中文与英语；未来新增语言时，**不得**在未评估影响
  的情况下削弱或破坏现有语言体验。
- 所有用户可见文案（包括错误提示、风险说明、引导文案等），**必须**通过统一
  的本地化资源管理进行维护（例如集中在 `lib/shared/l10n` 或等价模块），
  禁止在业务代码中硬编码中文或英文字符串。
- 每个新特性的规格文档，**必须**说明：支持的语言范围、关键文案示例，以及涉
  及的时间、数字、货币等格式差异。
- App **应**提供可预期的语言切换行为（例如遵从系统语言，或在设置页中显式选
  择语言）；在技术可行的前提下，用户在切换语言后，关键界面**应**无需重启 App
  即可生效，如做不到需在计划中说明原因。
- UI 设计与布局**必须**考虑不同语言长度差异，避免中英文或其他语言下出现截断、
  重叠等问题，优先采用自适应布局与弹性空间。
- 与交易和资金相关的风险提示与错误信息，在不同语言版本中的含义**必须**保持
  等价，不得出现语义弱化或模糊的情况。

理由：CybitX 需要服务不同地区与语言背景的用户，多语言体验直接影响信任、转化
与留存；同时，多语言也是满足监管沟通与合规披露要求的重要手段。

## 平台与技术约束

本项目是一款基于 Flutter 的 CEX 移动应用，必须遵守以下技术约束：

- Flutter SDK 版本：**3.38.1**。工程配置与 CI **必须**固定在该版本或清晰
  说明兼容范围。
- 语言：开启空安全（null safety）的 Dart。
- 状态管理：**统一使用 Riverpod** 作为应用共享状态的标准方案；如需引入
  其他全局状态管理框架，**必须**给出充分理由并通过评审。
- 目标平台：iOS 与 Android。桌面端、Web 或其他平台可在未来探索，但不属于
  本版本宪章的范围。
- 后台业务服务：基于 Node.js 技术栈（例如 NestJS/Express 等）负责核心业务逻辑
  与数据存储/交互。移动端在设计接口、数据模型与错误处理时，**必须**与后端
  契约保持一致，并避免与具体框架实现产生不必要耦合。
- UI 组件**推荐**通过统一的设计系统模块实现（例如 `lib/shared/ui`），以在
  行情、合约、现货、跟单、资产等区域保持一致的视觉与交互规范。
- 导航**必须**使用集中式方案（例如约定好的路由框架与配置），避免在各个
  特性模块中散落"临时"路由与深链处理。

如需偏离上述约束，**必须**在对应规格与实现计划中进行说明，并给出清晰的
权衡分析。

## 业务功能范围约束

CybitX 的各业务模块在不同版本中可能处于不同的实现阶段。本章节明确各模块的
当前功能范围，以避免误解与过度设计。

### 跟单模块（Copy Trading）

**当前版本范围**：跟单模块在当前版本中定位为**展示型功能**，主要目标是向用户
呈现跟单相关的核心信息与逻辑，**不包含**实际的跟单交易执行能力。

- **包含的功能**：
  - 交易员列表展示（排名、收益率、跟随人数、胜率等关键指标）；
  - 交易员详情页（历史收益曲线、交易记录、持仓情况、风险指标等）；
  - 跟单信号展示（实时推送交易员的开仓/平仓信号，通过 WebSocket 实现）；
  - 跟单收益模拟展示（假设用户跟单后的收益计算与展示）；
  - 跟单历史记录（用户曾关注或模拟跟单的交易员记录）。
- **不包含的功能**：
  - 实际跟单交易执行（即：用户点击"跟单"后，系统不会自动为用户下单）；
  - 跟单资金管理（例如：设置跟单金额、止盈止损、跟单比例等）；
  - 跟单订单管理（例如：查看、修改、取消跟单产生的订单）。
- **UI 与文案要求**：
  - 跟单模块的 UI **必须**通过适当的文案或标识（例如："当前为展示模式"
    "即将上线"等），向用户清晰说明该功能的当前状态；
  - 任何可能让用户误以为可以执行实际跟单交易的交互元素（例如："立即跟单"
    按钮），**必须**在规格文档中明确其行为（例如：跳转到说明页、收集用户
    意向等），并在实现中避免误导。

**未来扩展方向**：当产品决策明确需要支持实际跟单交易执行时，**必须**通过修订
本宪章（次版本或主版本更新）来正式纳入该能力，并在规格、计划与任务中给出
完整的安全、合规、风控与用户体验设计。

理由：明确功能范围可以避免团队在实现过程中产生误解，也可以让用户对产品能力
有正确的预期；跟单交易执行涉及资金安全与合规风险，必须在充分准备后再纳入。

## 项目结构与前后端分离

CybitX 采用前后端分离架构，Node.js 后端服务与 Flutter 移动端**必须**在物理
目录上独立，但在逻辑上协作，共同为用户提供完整的交易体验。

### 目录结构约定

- **backend/**：Node.js 后端服务的独立文件夹，包含所有业务逻辑、数据持久化、
  API 接口实现、中间件、配置与后端测试。
  - 后端**必须**拥有独立的 `package.json`、依赖管理、构建脚本与部署配置。
  - 后端**必须**在 `backend/README.md` 中说明技术栈、启动方式、环境变量要求
    与本地开发指引。
- **mobile/**：Flutter 移动端的独立文件夹，包含所有 Dart 代码、UI 组件、状态
  管理、移动端测试与平台特定配置（iOS/Android）。
  - 移动端**必须**拥有独立的 `pubspec.yaml`、依赖管理与构建配置。
  - 移动端**必须**在 `mobile/README.md` 中说明 Flutter 版本、启动方式、环境
    配置与本地开发指引。
- **specs/**：功能规格、实现计划、任务列表与 API 契约文档的集中存放位置，
  供前后端共同参考。

### 前后端职责边界

- **后端职责**：
  - 核心业务逻辑（用户认证、订单管理、资产计算、风控、KYC/AML 等）；
  - 数据持久化与查询（数据库、缓存、消息队列等）；
  - 对外提供 RESTful API 或 WebSocket 接口，供移动端调用；
  - 日志、监控、告警与后端可观测性基础设施。
- **移动端职责**：
  - UI 呈现、用户交互与本地状态管理；
  - 调用后端 API 获取业务数据，并在本地进行必要的缓存与展示优化；
  - 移动端特定的安全存储（例如 Keychain/Keystore）、生物识别、推送通知等；
  - 移动端日志、埋点与可观测性数据上报。

### 接口契约管理

- 前后端**必须**通过明确的 API 契约进行协作，契约文档**推荐**使用 OpenAPI/
  Swagger 或等价规范，并集中存放在 `backend/docs/api/` 或 `specs/contracts/`。
- 任何 API 变更（新增接口、修改参数、调整错误码等），**必须**先更新契约文档，
  并在规格或计划中说明对移动端的影响。
- 后端**应**提供契约测试（Contract Tests），确保实际接口行为与文档一致；
  移动端**应**基于契约编写集成测试，验证与后端的协作正确性。

#### RESTful API 与 WebSocket 协议分工

- **RESTful API**：用于请求-响应模式的业务操作，例如：用户登录/注册、下单、
  平仓、充提币申请、账户设置修改、历史数据查询等。
- **WebSocket**：**必须**用于实时数据流推送，包括但不限于：
  - **行情数据**：实时价格、深度、成交记录等市场行情推送；
  - **K线图数据**：实时 K线更新与历史 K线订阅；
  - **跟单数据**：跟单信号、跟单订单状态变更、跟单收益实时更新等；
  - **订单与仓位更新**：用户订单状态变更、持仓变动、资产余额变化等实时通知。
- WebSocket 契约文档**必须**定义：
  - 连接端点（例如 `wss://api.example.com/ws`）与认证方式（例如 token 参数
    或首条消息认证）；
  - 消息格式（推荐 JSON，需提供 JSON Schema 或等价规范）；
  - 订阅/取消订阅协议（例如：`{"action": "subscribe", "channel": "market.btcusdt"}`）；
  - 心跳机制（ping/pong 或应用层心跳消息）与超时策略；
  - 错误码定义与异常场景处理（例如：订阅失败、权限不足、连接断开等）；
  - 重连策略建议（例如：指数退避、最大重试次数等）。

### 独立部署与本地联调

- 后端与移动端**必须**能够独立构建、测试与部署，互不阻塞。
- 本地开发时，移动端**应**能够通过配置（例如环境变量或配置文件）指向本地
  后端服务（例如 `http://localhost:3000`）或远程开发/测试环境。
- 后端**应**提供健康检查接口（例如 `/health` 或 `/api/health`），供移动端
  与运维系统验证服务可用性。

理由：前后端分离可以让团队并行开发，降低耦合，提高迭代速度；明确的契约与
独立部署能力，是保证协作质量与系统可维护性的基础。

## 开发流程与质量关卡

CybitX 的开发流程围绕 speckit 工具链与本宪章展开。

- 每一项有实际业务价值的特性或重构，**应**遵循以下顺序：
  - 使用 `/speckit.specify` 编写规格，描述用户路径、需求与成功标准；
  - 使用 `/speckit.plan` 编写实现计划，进行宪章检查，明确架构决策与目录
    结构变更；
  - 使用 `/speckit.tasks` 生成任务清单，并按用户故事组织任务。
- 代码评审（Code Review）**必须**：
  - 检查实现是否符合规格、计划与任务清单；
  - 明确审视：是否遵守"安全与合规优先""交易体验与性能""领域边界"
    "可观测性"等核心原则；
  - 对违反强制性原则但未获豁免的改动，**必须**予以拦截。
- 对关键用户路径（例如：首登、KYC、充币、提币、下单与平仓、资产查看等），
  在发布前至少满足其一：
  - 已有覆盖端到端流程的自动化测试（单测 / 组件 / 集成测试）；或
  - 已建立明确的人工测试清单，并在发布流程中执行。

质量关卡可以随时间逐步收紧（例如提高测试覆盖率要求），但在未经过治理
流程修订宪章之前，**不得**随意降低要求。

## 治理机制

本宪章约束 CybitX CEX 应用的整体设计与实现方式。当现有习惯或遗留模式与
本宪章冲突时，以宪章为准。

- 任何功能实现、重构或依赖引入，**必须**对照本宪章的核心原则与相关章节
  进行评估。
- 修改宪章时，**必须**：
  - 以书面形式提出（例如通过 Pull Request），给出清晰的动机与影响分析；
  - 标明本次修改是"主版本/次版本/补丁版本"中的哪一种（见下方版本策略）；
  - 在原则显著收紧或变更时，给出迁移/推广方案。
- 版本策略：
  - **主版本（X.0.0）**：删除或根本性重写原则，或引入不向后兼容的治理规则；
  - **次版本（0.Y.0）**：新增原则或章节，或大幅扩展现有指导，对未来工作
    有实质约束，但不否定历史已合规实现；
  - **补丁版本（0.0.Z）**：文字澄清、错别字修正或不改变语义的细微优化。
- 合规审查：
  - 评审者在审查较大改动时，**应**显式说明其与宪章的一致性；
  - 对于复杂或跨领域的需求，**建议**在规格或计划中增加"宪章影响"章节，
    说明该改动与现有原则之间的关系。

运行期开发指引（如 quickstart、编码规范、Playbook 等），**必须**与本宪章
保持一致；当两者冲突时，在宪章修订之前，以本宪章为最终依据。
